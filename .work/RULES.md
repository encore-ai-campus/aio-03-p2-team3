## 1. 원칙
- 레포가 유일한 원본이다. 진행 상황과 결정은 레포 파일, Issue, PR을 기준으로 말한다. 메모리나 지난 대화에 남은 상태로 답하지 않는다. [Past work: setup]
- 필요한 파일만 읽는다. `.work/TASK.md`의 파일 지도로 위치를 찾고 그 파일만 연다. [Past work: setup]
- 문서는 실제 코드와 파일 내용대로 쓴다. 없는 기능을 지어내지 않는다. 문서와 코드가 다르면 코드를 기준으로 고치고 PR에 차이를 적는다. [Past work: aio3]
- 요청 범위 밖의 파일은 고치지 않는다. 꼭 고쳐야 하면 먼저 이유를 말하고 허락을 받는다. 중간에 물을 수 없는 작업(Codex 작업)에서는 고치지 않고 결과에 '범위 밖 수정 필요: 파일, 이유'를 적는다. [Past work: aio3 · Claude proposal]
- 요청이 모호하거나 요청자만 정할 수 있는 결정(기능 범위, 화면 문구, 상태·데이터 구조)이 있으면 추측하지 않는다. 대화라면 먼저 묻는다. 중간에 물을 수 없는 작업이면 구현하지 않고 질문을 결과로 돌려준다. [Past work: aio3 · Claude proposal]
- 사용자가 꼭 보고 정하거나 해야 할 사항(요청자가 정할 것, 규칙 변경 제안·변경, 요청과 다르게 한 것, 사용자가 직접 할 일·병합 순서)은 답의 앞부분에 `❗ 확인할 것:` 목록으로 모아 눈에 띄게 쓴다. 본문 중간이나 끝에 묻어 두지 않는다. PR 답에서 놓는 자리는 5절 5번을 따른다. [Request]
- 이 레포만의 규칙은 `.work/TASK.md`에 둔다. 공통 규칙의 예외가 필요하면 TASK.md에 '공통 규칙 N절 예외: 이유'로 적고, 이 레포 안에서는 그 예외가 우선한다. [Past work: setup]

## 3. 작업하면서
- 작업 하나 = 브랜치 하나 = PR 하나. `main`에 직접 push하지 않는다. [Past work: aio3]
- 브랜치 이름은 `feat/`·`fix/`·`docs/` 뒤에 작업명(영어 소문자·하이픈)을 붙인다. [Past work: aio3] Codex가 PR을 만들 때 스스로 정하는 브랜치 이름은 그대로 둔다. [Claude proposal]
- 병합된 PR의 브랜치에는 push하지 않는다(그 커밋은 `main`에 들어가지 않는다). 답에 PR 링크를 준 뒤 받은 후속 요청은 앞 PR에 더하지 않는다. 앞 PR이 병합됐는지 확인해(`gh api repos/<레포 주소>/pulls/<번호> --jq .merged_at`) 병합됐으면 최신 `main`에서, 병합 전이면 앞 PR 브랜치 위에서 새 브랜치를 만들어 `main`으로 새 PR을 연다(병합 전이면 두 PR을 순서대로 병합하거나 새 PR만 병합해도 된다고 답에 적는다). 요청자가 병합 전 그 PR을 고쳐 달라고 할 때(CI 오류, 5절 7번 충돌)는 예외다. [Request]
- Claude는 브랜치를 `git remote set-branches --add origin <브랜치>` 뒤 `git push -u origin <브랜치>`로 올린다(얕은 복제는 `main`만 추적해서 `-u`만으로는 원격 브랜치와 연결되지 않는다). [Past work: setup]
- 커밋 메시지는 한국어로 쓰고, 앞에 `feat:`·`fix:`·`docs:`를 붙인다. [Past work: aio3]
- 기존 파일은 바뀐 부분만 고친다. 통째로 다시 쓰지 않는다(새 파일은 예외). [Past work: setup]
- 비밀값(API 키, 토큰, 계정 정보)과 실제 개인정보(실명, 연락처, 이메일, 일정 원문)는 코드·테스트·문서·예시 데이터·로그에 넣지 않는다. 새 환경변수는 `.env.example`에 이름과 설명만 적는다. [Past work: aio3]
- 패키지는 버전을 고정해 추가한다. 방법은 TASK.md를 따른다. [Past work: aio3]
- TASK.md의 '공통 부분'을 고치면 PR 양식의 '공통 부분 변경' 칸에 파일, 이유, 영향, 조율한 팀원을 적는다. [Past work: aio3]

## 4. 규칙 파일을 고칠 때
규칙 파일은 `AGENTS.md`, `.work/RULES.md`(이 파일), `.work/TASK.md`, `.github/pull_request_template.md`다. [Request]
1. 요청자가 바꾸라고 했을 때만 고친다. 바꿀 만한 점을 발견하면 답변에서 제안만 한다. 앞으로도 지킬 작업 방식을 요청받았는데 규칙 파일에 없으면 넣자고 제안한다. [Past work: setup]
2. 고치기 전에 고칠 규칙 파일 전체를 읽는다. [Past work: setup]
3. 요청을 추가·수정·삭제로 나눈다. 같은 내용을 다루는 규칙이 이미 있으면 새 줄을 덧붙이지 않고 그 줄을 고친다. 새 규칙과 충돌하는 규칙은 고치거나 지우고, 더는 맞지 않는 규칙은 지운다. [Past work: setup]
4. 어느 쪽을 남길지처럼 요청자가 정해야 하는 충돌은 고치기 전에 묻는다. 물을 수 없으면 고치지 않고 결과에 충돌을 적는다. [Past work: setup · Claude proposal]
5. 고친 뒤 파일 전체를 다시 읽어 겹치거나 충돌하는 규칙이 없는지 확인한다. [Past work: setup]
6. PR의 '⚠ 규칙 변경'에 추가·수정·삭제를 한 줄씩 적는다. 수정은 '전 → 후'로 적는다. 병합이 곧 승인이다. [Past work: setup]

## 5. 끝낼 때 (파일을 바꾼 경우)

2. 파일을 더하거나 지우거나 옮겼으면 `.work/TASK.md`의 파일 지도도 고친다. [Past work: setup]
3. 검사 도구(`python3 .work/check.py`)가 있으면 통과시킨다. 통과하지 못하면 PR을 열지 않고 먼저 고친다. 고칠 수 없으면 오류와 시도한 방법을 알린다. [Past work: aio3] 테스트(`uv run pytest`)도 함께 직접 실행해 통과시키고, 두 실행 결과를 마지막 답에 보인다. [Request]
4. PR 설명은 `.github/pull_request_template.md` 양식을 모두 채운다. [Past work: aio3] Codex는 요청에 적혀 있지 않아도 3번을 마친 뒤 새 브랜치에 커밋해 GitHub에 push하고, `main`으로 PR을 열어 본문에 양식을 채우고, 마지막 답에도 같은 설명을 낸다. [Request]
5. 마지막 답 맨 앞 줄: Claude는 `🔔 PR을 날렸습니다. 병합 후 진행해주세요: <PR 링크>`, Codex는 `🔔 PR을 열었습니다. 확인 후 병합해 주세요: <PR 링크>`를 쓴다. 공통 부분을 바꿨으면 바로 아래에 `⚠ 공통 부분 변경: 병합 전에 <관련 팀원>과 조율해 주세요.`를 쓴다. 그 아래에 1절의 `❗ 확인할 것:`을 쓴다(있을 때). 그 뒤에 바꾼 내용을 짧게 적는다. [Request · Claude proposal]
6. AI는 PR을 병합하지 않는다. 병합은 사람이 한다. [Past work: setup · aio3] 승인 없이 PR을 연 사람을 포함해 누구나 병합한다. 필수 리뷰 같은 브랜치 보호 규칙은 두지 않는다. 병합한 브랜치는 지우지 않는다. [Request]
7. 충돌: 앞 PR이 병합된 뒤 충돌이 나면 요청자가 그 PR에서 AI에게 최신 `main` 흐름에 맞게 고쳐 달라고 한다(Codex는 PR 댓글 `@codex 최신 main에 맞게 충돌을 고쳐 주세요`). AI는 양쪽 변경의 뜻을 모두 살려 고치고, `docs/PROJECT_CONTEXT.md`의 해당 절도 합친 결과대로 고친다. [Request] 그렇게 되지 않으면 GitHub 웹 화면에서 고치거나, PR을 닫고 최신 `main`에서 같은 작업을 다시 낸다. [Claude proposal]

- "진행기록을 봐서 알려주세요"를 들으면 STATUS.md를 읽고 '지금 할 일'과 '대기'를 알려 준다. [Past work: setup]
- 파일을 열지 못하면 못 열었다고 말한다. 기억이나 지난 대화로 짐작해 답하지 않는다. [Past work: setup]

## 7. 큰 작업 나누기 (모든 AI)
1. 기능이 둘 이상 섞인 요청(예: 도구 여럿 추가, 도구 추가와 그래프 구조 변경)은 구현하지 않고, 계획 파일 `docs/plans/<작업명>.md`만 만들어 PR로 올린다. [Request]
2. 계획 파일에는 목표와 하위 작업을 적는다. 하위 작업은 `## N. 제목` 절 하나씩이고, 절마다 할 일, 완료 기준, 영향받는 상태·도구·노드, 섞지 않을 것을 적는다. 하위 작업 하나 = 기능 하나 = 작업 하나 = PR 하나다. [Request · Past work: setup]
3. 하위 작업들이 서로 맞춰야 할 것(상태 필드 이름, 도구 입출력 형식)은 첫 하위 작업에서 정해 파일로 남기고, 뒤 하위 작업이 그 파일을 읽게 한다. [Past work: setup]
4. 계획 PR이 병합되면 하위 작업마다 새 작업(Codex는 새 작업, 대화는 새 대화)을 시작해 `docs/plans/<작업명>.md`의 그 절만 읽는다. 다른 하위 작업을 같은 작업의 후속 요청으로 잇지 않는다(Codex는 길어지면 자동으로 요약하며 세부를 잃을 수 있다). [Request · Claude proposal]
5. 하위 작업을 마치면 같은 PR에서 계획 파일의 그 절 제목 끝에 `(완료)`를 붙인다. [Claude proposal]
6. 끊긴 뒤 다시 할 때는 작업 브랜치의 파일과 커밋을 먼저 확인하고 남은 일만 한다. [Past work: setup]
7. 이 절에는 KB로 작업량을 재지 않는다. KB 재기는 Claude 도구 기준이라 8절 세팅 단계 작업에만 쓴다. [Request]

## 8. 세팅 단계 작업 (Claude)
세팅 단계(`.work/FLOW.md`의 번호대로 새 대화에서 한 단계씩 하는 작업)의 작업량을 재고 넘치면 나누는 규칙이다. [Past work: setup] 재는 도구는 `.work/measure.py`이고(크기만 내고 파일 내용은 대화에 넣지 않는다) 단위는 KB다. 레포 주소는 TASK.md에 있다. [Past work: setup]

### 작업량 재기
1. 작업량 = 시작할 때 읽는 파일 + 읽을 파일 + 첨부할 파일 + 실행 중 생기는 양 + 만들 것. 실행 중 생기는 양은 도구별 예상 횟수 × 1회 크기다(`--tools 웹검색=3 스크립트=5`). 같은 절차를 되풀이하면 횟수를 곱한다. [Past work: setup]
2. 레포 밖 파일은 `이름=KB`, 모르면 `이름=?`. 텍스트가 아닌 파일은 텍스트로 뽑아 잰 크기를 넣는다. 표에 없거나 1회 크기가 크게 다른 도구는 `종류=횟수x크기`, 횟수를 모르면 `종류=?`. [Past work: setup]
3. 다음 단계 안내를 쓸 때 그 단계 대화 1회의 작업량을 안내와 함께 적는다. 같은 대화에서 새 요청을 받으면 이 대화에 쌓인 양에 새 일을 더해 잰다. [Past work: setup] 넘으면 묻지 않고 정한 것·남은 일·읽을 파일을 파일로 남기고, 새 대화로 넘길 안내를 적어 넘긴다. [Request]
4. 서브에이전트는 돌려받는 결과만 센다. 서브에이전트 안의 일은 따로 재서 기준 이하로 두고, 돌려받을 결과의 크기와 형식을 지시에 적는다. [Past work: setup]
5. 기준은 100KB, 도구 1회 크기는 `measure.py`의 표다. 둘 다 처음 값이라 '최근 완료'의 기록(사용 한도, 자동 요약)을 보고 이 레포에서 고친다. [Past work: setup · Request]

### 대화 하나에 둘 일
1. 같은 절차를 다른 입력으로 돌리는 실행은 대화를 나누고, 견주기는 결과 파일만 읽는 단계로 따로 둔다. [Past work: setup]
2. 뒤 일의 근거가 되는 중간 결과(조사 결과, 후보, 판정)는 만들 때마다 파일로 저장해 작업 브랜치에 커밋·push한다. [Past work: setup]
3. 끊긴 뒤에는 작업 브랜치의 저장 파일과 커밋을 먼저 확인하고 남은 일만 한다. 비용 없는 확인(파일 확인)은 막지 않는다. [Past work: setup]

### 작업 흐름
- 세팅 단계 목록은 `.work/FLOW.md`에 둔다. 단계마다 `## N단계 …` 절로 나누고 `- 할 일:` `- 읽을 것:` `- 만들 것:` `- 섞지 않을 것:` `- 도구:`(예상 횟수 또는 `없음`) 줄을 둔다. [Past work: setup]

### 단계를 마칠 때 (PR을 만들기 전)
1. `.work/STATUS.md` '지금 할 일'의 다음 단계 항목 아래에 들여 써서 다음 단계 안내를 적는다. 형식은 아래로 고정한다. 읽을 파일의 발췌는 `경로#절 제목`으로 적는다. 명령어는 짧게, 자세한 지시는 FLOW.md의 그 단계 절에 둔다. [Past work: setup]
   ```
   - [ ] N단계 <제목> — <완료 기준>
     - 명령어: <붙여넣을 명령어>
     - 첨부: `이름=KB` … 또는 없음
     - 읽을 파일: `경로` `경로#절 제목` …
     - 읽지 않을 파일: …
     - 만들 파일: `이름=KB` …
     - 도구: `종류=횟수` … 또는 없음
     - 작업량: 약 ○KB(실행 중 ○KB 포함) / 기준 ○KB
   ```
2. 안내의 백틱 항목을 그대로 넘겨 `python3 .work/measure.py --read <읽을 파일> --attach <첨부> --make <만들 파일> --tools <도구>`로 잰다. 시작할 때 읽는 파일은 `--start AGENTS.md .work/RULES.md .work/TASK.md .work/STATUS.md docs/PROJECT_CONTEXT.md`로 준다(AGENTS.md가 시작할 때 읽게 하는 파일 모두). [Past work: setup · Claude proposal]
3. PR 답변의 🔔·⚠·❗ 줄(5절 5번) 아래에 결과를 쓴다. [Past work: setup]
   - 기준 이하: `다음 단계(N단계) 작업량: 약 ○KB(실행 중 ○KB 포함) / 기준 ○KB — 새 대화 하나에서 하기에 적당합니다.` 그 아래에 붙여넣을 명령어와 첨부할 파일을 적는다.
   - 기준 초과: 묻지 않고 같은 PR에서 작업 배분량 검토를 해 나눈다. 🔔 줄 아래에 `다음 단계(N단계)가 기준을 넘어(약 ○KB / 기준 ○KB) N-1, N-2로 나눴습니다.`를 쓰고, 이어서 첫 하위 단계를 기준 이하 형식으로 쓴다. [Request]
   - 크기 모름: 모르는 파일과 나머지 양을 적고, 크기를 알려 주면 다시 잰다고 쓴다.
4. 마친 단계는 안내 줄을 지우고 '최근 완료'에 `- 날짜 N단계 제목 — 작업량 약 ○KB(실행 중 ○KB) · 사용 한도: 걸림/안 걸림/모름 · 자동 요약: 있음/없음/모름` 형식으로 옮긴다. [Past work: setup]

### 작업 배분량 검토
다음 단계가 기준을 넘을 때 묻지 않고 바로 한다. "작업 배분량 검토를 해주세요"를 받았을 때도 한다. [Request · Past work: setup]
- 따로 요청받아 할 때는 방금 마친 단계의 PR이 병합됐는지 먼저 확인한다(`gh api repos/<레포 주소>/pulls/<번호>`의 `merged_at`). 병합 전이면 병합 후 알려 달라고 하고 멈춘다. [Past work: setup]
- 나눈 하위 단계마다 다시 재서 모두 기준 이하가 되게 나눈다. 같이 처리해야 할 것(서로 맞춰야 하는 이름·형식, 앞뒤가 이어지는 수정)은 한 하위 단계에 둔다. 따로 정하면 어긋날 것은 앞 하위 단계에서 정해 파일로 남긴다. [Past work: setup]
- 파일 하나가 혼자 기준을 넘으면 발췌(`--outline <파일>`로 절과 크기를 보고 필요한 절만), 뽑기(무거운 조회 결과를 그대로 작은 파일로 남기는 하위 단계를 앞에 둠), 이어 하기, 서브에이전트 중 맞는 방법을 쓴다. 어느 것도 맞지 않으면 기준을 넘는 채로 두고 이유를 안내와 PR에 적는다. [Request]
- 나눈 안(하위 단계별 할 일, 파일과 크기, 작업량, 나눈 이유)은 확인받지 않고 반영하고, PR '무엇을 바꿨나'와 답에 적는다. [Request]
- N단계를 나누면 N-1, N-2 …로 이름을 붙이고 뒤 단계 번호는 그대로 둔다. 원래 N단계 항목은 묶음 제목으로 남겨 'N-1, N-2로 나눔(날짜, 이유)'을 적는다. FLOW.md와 STATUS.md를 한 PR에서 함께 고친다. [Past work: setup]

### 새 대화에서 넘겨받을 때
- STATUS.md에 그 단계의 안내가 있으면, 시작할 때 읽는 파일 말고는 안내에 적힌 파일만 읽는다. 발췌는 `python3 .work/measure.py --show '<경로>#<절 제목>'`으로 그 절만 연다. [Past work: setup]
- 읽지 않을 파일은 열지 않고, 그 내용을 지난 대화나 메모리에서 찾지도 않는다. [Past work: setup]
- 첨부할 파일이 오지 않았으면 요청한다. 받은 뒤 다시 재서 기준을 넘으면 묻지 않고 작업 배분량 검토만 해서 PR로 올리고 끝낸다. [Past work: setup · Request]
