# MVP 계획 인계 (2026-11-09)

요청자가 MVP 구현을 준비하며 정한 것, Claude가 확인한 사실과 추천 설계, 남은 세 대화(규칙 변경 1 → 규칙 변경 2 → MVP 계획) 안내를 담는다. 각 대화는 4절의 자기 절이 가리키는 부분만 읽는다. 계획 PR이 병합되면 이 파일은 기록으로 두고 고치지 않는다. [Claude proposal]

## 1. 정한 것
1. 서비스 흐름: 사용자의 Gmail에 메일이 오면(Gmail 푸시 알림, 시간 단위 실행 아님) 에이전트가 메일을 분석해 답장 후보 2~3개를 만든다. 사용자가 하나를 골라 승인해야만 보낸다. 승인 없이는 어떤 메일도 보내지 않는다. 상대방 답장에 거래 내용이 있으면 인보이스 필수 항목을 먼저 검토하고, 빠진 항목이 있으면 견적서를 만들지 않고 재질문 답장 후보를 만든다(이것도 승인 뒤 발송). 다 있으면 견적서를 만든다. [Request]
2. 사용자: 서비스를 쓰는 사람(11/19 체험하는 다른 팀 포함)을 '사용자'라 부른다. 사용자는 여럿이고 각자 자기 Gmail을 등록(Google 로그인)해 쓴다. 발표 시연도 팀원 한 명이 사용자로 자기 Gmail을 등록해 한다. '상대방'은 사용자에게 메일을 보내는 거래 상대다. [Request]
3. 문서: MVP는 견적서만 만든다. 화면에서 확인·승인하면 답장에 PDF로 첨부해 보낸다. 계약서는 나중에 같은 거래 항목으로 틀만 더한다. [Request]
4. API: Gmail API와 Cloud Pub/Sub(푸시 알림용)를 더한다. LLM은 Gemini(`gemini-3.8-flash`) 그대로, Google Calendar는 도구 2용으로 남긴다. 특일 정보·단기예보·네이버 지역 검색·길찾기는 MVP에서 빼고(`.env.example`에서도 뺌) `.work/design/api-choice.md`에 '일정 도구 추천 후보'로 남긴다. `docs/PROJECT_CONTEXT.md` 4절에 '일정(캘린더) 도구 작업 때 AI가 이 후보를 요청자에게 추천한다'를 적어, 팀원이 일정 도구를 맡을 때 추천으로 뜨게 한다. [Request]
5. 배포: Render 무료를 계속 쓴다. 시연 때는 창을 여러 개 미리 열어 서버를 깨워 둔다. [Request]
6. 도구 1~3(이미지→견적서, 구글캘린더 등록, 검토)은 팀원이 나중에 더한다. 지금은 더하기 쉬운 구조만 만든다. 그 도구의 API·계정 등록은 그 도구를 더할 때 한다. Gmail·Pub/Sub·Render·Postgres 설정은 MVP라 지금 한다. [Request]
7. 도구는 같은 서버 안의 LangGraph 도구 함수로 두고 그 안에서 실제 외부 API를 부른다. 별도 서버로 떼지 않는다(왕복 지연이 늘어 속도 요구와 부딪침). 과제 원문에 '도구가 서비스 밖에 있어야 한다'는 조건은 없다(2절). [Request: 조건 확인 요청 · Claude proposal]
8. 기억 저장소: Render 무료 Postgres(웹 서비스와 같은 지역). 만든 지 30일 뒤 만료라 11/19 제출까지는 충분하다. [Claude proposal]
9. 화면은 세련되게, 나중에 고쳐도 오류 없이 반영되게 만든다. 서버 응답은 빠르게 한다(프로젝트1 Aio3에서 응답이 느렸음). [Request]
10. PR 설명: PR을 연 팀원이 발표 질문(이 기능을 어떤 방식으로 구현했나)에 답할 수 있고, 그 설명만으로 바이브코딩이 될 정도로 안내한다. 수동 코딩이 필요한 수준의 설명은 하지 않는다. 규칙 변경으로 반영한다(4-1). [Request]
11. 추적 기록: 결과만이 아니라 디버깅 때 거꾸로 따라갈 수 있는 기록을 남긴다. 코드 변경은 git·PR('오류·재실행 기록' 칸)에 이미 남으므로, 실행 기록(실행마다 노드 전이·도구 호출·오류·재시도·소요 시간)을 기능으로 만든다. [Request · Claude proposal: 해석]

## 2. 확인한 사실 (2026-11-09 조회)
공식 문서로 확인:
- Gmail 푸시 알림은 Cloud Pub/Sub로 전달된다. `users.watch`는 최소 7일마다 다시 호출해야 하고 하루 1번이 권장된다. 출처: https://developers.google.com/gmail/api/guides/push
- Google OAuth: 게시 상태가 테스트면 테스트 사용자의 승인(갱신 토큰 포함)이 7일 뒤 만료된다. 검증 안 된 앱이 민감·제한 범위를 쓰면 경고 화면이 뜨고 새 사용자 100명 한도가 있다. 출처: https://support.google.com/cloud/answer/15549945 , https://support.google.com/cloud/answer/13463817
- Render 무료 웹 서비스: 15분 동안 들어오는 요청(HTTP 요청·WebSocket 메시지)이 없으면 잠들고, 다음 요청 때 깨는 데 최대 약 1분 걸린다. `/robots.txt` 요청으로는 깨지 않는다. 재배포·재시작·잠들 때 로컬 파일(SQLite 포함)이 사라진다. 유료 인스턴스는 잠들지 않는다. 무료 Postgres는 만든 지 30일 뒤 만료되고 14일 유예 뒤 지워진다. 출처: https://render.com/docs/free , https://docs.render.com/faq
- 과제 원문(Notion, 내장 브라우저로 읽음): 도구가 서비스 밖에 있어야 한다는 조건은 없다. 요구는 실제 API 데이터 사용, 실제로 접근할 수 있는 API와 어떤 조건에서 어떤 도구를 고르는지 정하기, 외부 API·기억 저장소의 원격 접근 확인이다. 노드·도구 수보다 선택 이유·상태 변화·오류 수정 결과를 확인할 수 있는지가 중요하다고 적혀 있다. 권장 순서는 대표 요청 하나를 화면 → 에이전트 → 도구 → 검증 → 결과 안내까지 먼저 잇고, 기억과 오류 수정 경로를 더하는 것이다.

제3자 문서로만 확인(해당 하위 작업에서 공식 문서로 확인):
- Pub/Sub 토픽에 `gmail-api-push@system.gserviceaccount.com` 게시자(Publisher) 권한을 줘야 알림이 온다.
- Gmail 범위: `gmail.readonly`·`gmail.modify`는 제한(restricted), `gmail.send`는 민감(sensitive) 범위다.

미확인(해당 하위 작업에서 확인):
- Pub/Sub를 쓰려면 결제 계정 연결이 필요한지(가격 페이지는 '결제 계정마다 월 10GiB 무료'라고 적음). 결제를 Gemini 키가 있는 프로젝트에 붙이면 Gemini 무료 등급에 영향이 있는지.
- OAuth를 프로덕션(검증 없음)으로 게시했을 때 Gmail 범위 토큰이 7일 뒤 만료되는지.
- 잠든 Render 서버가 깨는 동안 Pub/Sub 푸시 요청이 어떻게 처리되는지(기다렸다 전달되는지, 실패 뒤 재전송되는지).

## 3. Claude 추천 설계 (계획에 반영한다) [Claude proposal]
속도
- 푸시 알림을 받으면 바로 응답하고, 뒤에서 답장 후보를 만들어 DB에 저장한다. 화면은 저장된 결과만 읽는다(사용자가 열 때 이미 준비돼 있음).
- LLM 호출을 줄인다. 답장 후보 2~3개는 한 번의 호출(구조화 출력)로, 거래 항목 추출은 한 번으로 한다. 필수 항목 검토는 코드 규칙으로 한다(LLM 없음). 성찰은 규칙 검사에서 문제가 나왔을 때만 LLM을 다시 부른다.
- 도구는 같은 서버 안의 함수로 두고, API 클라이언트와 DB 연결은 재사용한다.
- 실행 기록에 노드별 소요 시간을 남겨 느린 곳을 바로 찾는다.
- 화면은 열려 있는 동안 1~2분마다 가벼운 요청으로 목록을 새로 읽는다. 새 후보를 바로 보여 주고, 창이 열려 있는 동안 Render 무료 서버가 15분 규칙으로 잠들지 않게 한다(1절 5번의 '창 미리 열기'가 효과를 내려면 필요).

정확성·안전
- 서비스가 보낸 메일도 메일함 변화라 알림이 온다. 사용자 자신이 보낸 메일은 처리하지 않고, 같은 알림·메일을 두 번 처리하지 않는다(메일 ID로 중복 제거).
- 상대방 답장은 Gmail 스레드(threadId)로 앞 대화와 잇는다.
- 후보와 승인 버튼은 로그인한 사용자 본인 것만 보인다. 승인 기록(언제, 어느 후보)을 남긴다.
- 감시 등록(`users.watch`)은 크론 없이 갱신한다. 로그인할 때, 알림을 받을 때, 화면 요청 때 마지막 갱신이 하루를 넘었으면 다시 호출한다.
- 개인정보: Gemini 무료 등급은 입력이 Google 제품 개선에 쓰이므로(`api-choice.md`) 화면에 '테스트용 Gmail로 등록하세요'를 안내한다(기존 결정). 자동 발송 메일(no-reply, 프로모션·소셜 분류)은 처리하지 않는다.
- Gemini 무료 한도는 프로젝트 단위라 사용자가 늘면 걸릴 수 있다. 한도 오류는 통신 실패 재시도와 구분해 화면에 안내하고 대체 경로를 둔다.
- Google 토큰은 DB에 암호화해 저장하고, 암호화 키는 환경변수로 둔다.
- 견적서 PDF는 한글 글꼴을 넣어 만든다(없으면 한글이 깨짐).

확장(팀원이 더할 도구)
- 도구 하나 = 파일 하나 + 등록 목록 한 줄로 더하게 하고, 입출력 형식은 공통 계약 파일에 둔다.
- OAuth 범위는 설정 목록 하나로 둔다. 캘린더 범위를 나중에 더하면 사용자가 다시 동의해야 한다.
- 화면은 색·글꼴·간격을 한 파일(디자인 토큰)에 모으고 화면 조각(컴포넌트)으로 나눠, 한 곳을 고쳐도 다른 곳이 깨지지 않게 한다.

과제 필수(MVP에 넣는다, R-ID는 `docs/REQUIREMENTS.md`)
- 다중 도구 선택(R-02): MVP 안에서 고를 도구가 여럿 있어야 한다(예: 답장 후보 만들기, 거래 항목 추출, 필수 항목 검토, 재질문 만들기, 견적서 만들기, 메일 보내기).
- 자가 성찰 루프와 켜기/끄기 스위치(R-09·R-10·R-13: 같은 입력으로 성찰 전후 비교).
- 단기 기억(메일 스레드 단위)·장기 기억(사용자 선호·회사 정보·상대방별 거래 기록)·긴 스레드 요약(R-06~R-08).
- 재시도 한도, 대체 경로, 정상·실패·추가 질문 종료 조건(R-11).
- 실행 기록(R-12, `docs/test-records/`), 설계서 초안(D-01, 11/13), 시험 보고서(D-02).

## 4. 남은 일과 새 대화 안내
순서: 4-1 규칙 변경 1 PR 병합 → 4-2 규칙 변경 2 PR 병합 → 4-3 MVP 계획 PR 병합 → 계획의 하위 작업(Issue)마다 새 작업. 4-4 템플릿 레포 반영은 4-2 병합 뒤에 하고, 4-3과는 순서가 없다(2026-11-09 요청자가 정함). 4-1~4-4는 Claude(이 프로젝트의 새 대화)에서 하나씩 한다. 요청자가 정할 것이 생기면 대화에서 묻는다. [Claude proposal]

규칙 변경은 고친 규칙 파일을 다시 끝까지 읽어야 해서(공통 규칙 4절 5번) 한 대화에 모으면 작업량이 기준(100KB)을 넘는다. 그래서 `.work/RULES.md`를 고치지 않는 4-1과 `.work/RULES.md`를 고치는 4-2로 나눴다. 4-2의 RULES 5절 5번이 4-1에서 더한 PR 양식 줄을 가리키므로 4-1을 먼저 한다. [Claude proposal]
