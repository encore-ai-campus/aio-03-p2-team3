## 설계 원칙과 채택 목표

1. 기존 정책 → parallel(8 workers) → serial(직렬)의 실행 경계와 실패 시 후속 단계 중단을 유지한다. worker 수를 더 늘리거나 순차 단계를 별도 병렬 풀로 실행하지 않는다.
2. 우선 불변 산출물만 재사용한다. 사용자·DB 데이터·브라우저 세션·가짜 공급자의 호출 목록·인증 정보는 테스트마다 새로 만든다.
3. 실제 프로세스 재시작, 키 교체/삭제, 소유권, 지연 재시도와 migration의 검증을 축소하거나 빠른 mock으로 대체하지 않는다.
4. 새 패키지·일반 캐시 프레임워크·공유 서비스는 기본안에 없다. 기존 fixture·가짜 공급자와 표준 라이브러리를 사용한다.
5. 최초 목표는 동일 환경의 순차 단계 중앙값 20% 감축이다. 기존 단일 349.92초를 참고하면 약 280초지만, 1절에서 기준을 확정한 뒤 목표를 재확인한다. 보장치나 완료 판정 수치로 미리 표시하지 않는다.
6. 순차 검사를 병렬로 옮기면 병렬 단계 시간이 늘 수 있다. 순차 수치만 줄이고 전체 파이프라인이 같거나 느려지는 변경은 성능 개선으로 채택하지 않는다. 나머지 비용이 같다는 가정에서 전체 약 450초를 참고 목표로 삼되 실제 전체 시간을 우선한다.

## 3. 실제 프로세스의 반복 시작 비용 축소

- 할 일: 1절에서 역할별 시작/종료 비용을 확인한 뒤 `tests/fakes/worker_process.py`의 역할별 import를 분리한다. 현재 최상위 `ChatOpenAI` import는 server/openai 역할에도 적용되므로 PC 역할에서만 필요한 SDK는 PC 분기로 옮기는 안을 검증한다. `tests/test_worker_process.py`는 측정상 이득이 있으면 불변 TLS 인증서/키 생성만 session 범위에서 재사용한다. 함수별 서버·가짜 OpenAI·PC 프로세스와 자격증명/DB는 새로 유지한다.
- 완료 기준: 기존 6개 worker 프로세스 사례와 Windows 전용 회귀가 통과한다. 역할별 시작 중앙값과 전체 모듈 시간이 줄고, 실제 SDK/HTTPS·두 사용자 격리·키 교체 재시작·해제 후 결과 거부·출력 비밀값 가리기가 유지된다. 모든 시작 실패/본문 실패/timeout에서도 생성한 PID만 회수한다. 이득이 없으면 해당 변경을 채택하지 않는다.
- 영향받는 상태·도구·노드: 테스트 전용 `tests/fakes/worker_process.py`, `tests/test_worker_process.py`의 준비 자원과 계측. 제품 worker/adapter/프로토콜·상태·노드 없음.
- 섞지 않을 것: PC 프로세스의 테스트 간 공유, 실제 프로세스 검사의 TestClient 대체, 상태를 초기화하지 않은 장기 실행 가짜 서버, 제품 SDK 옵션·타임아웃 변경.
- 선행 작업: 1절. 2절과 다른 파일이므로 병행 가능하다.
- 하는 사람: Codex.

유지할 시간/동작 경계:

- `SLOW503`은 실제 6초 지연 × 3회와 기존 재시도 예산을 유지한다. 과거 HTTP 읽기 15초 한도 문제를 재현하는 검사이므로 이 지연을 fake timer나 즉시 응답으로 바꾸지 않는다.
- SDK 20초, 서버 전체 120초, 시험 HTTP 125초(연결 5초), 정상 종료 대기 35초는 유지한다. 특히 35초는 `communicate()`의 **최대 대기**이며 매번 35초를 소비한다는 의미가 아니다. 실제 종료가 느리면 원인을 고치고 상한만 줄여 성공시키지 않는다.
- 준비 대기는 이미 `/healthz`·가짜 공급자 상태를 확인하는 poll이다. 현재 0.05초/0.01초 poll을 무조건 고정 sleep으로 대체하거나 불필요한 준비 대기 최적화를 주장하지 않는다.
- 키 교체/삭제 검사는 파일을 바꾸고 실제 PC 프로세스를 다시 시작하는 순서를 유지한다. 함수별 가짜 호출 목록과 쿠키/CSRF·DB는 공유하지 않는다. log pipe 처리는 기존 비밀값 검사와 회수 보장을 유지하며, 병목이 입증되지 않은 새 log collector는 도입하지 않는다.

## 4. DB 서버 재시작과 DB 격리를 분리

- 할 일: 1절의 DB 비용 결과를 읽고 상위 #220에 연결한다. `test_worker_postgres.py`의 `pgweb` 4개 사례는 공통 테스트 서버 + 테스트별 새 `database_url`을 사용하는 안으로 바꾼다. 기존 사용자 upgrade 1개도 서버 재시작 자체를 검증하는지 확인한 뒤, 클러스터 수명과 무관하면 같은 서버의 별도 빈 DB에서 수행한다. 서버 수명 검증이 필요하면 그 사례만 자체 서버를 유지한다.
- 완료 기준: 실제 PostgreSQL/pgvector·서로 다른 엔진/연결의 claim·완료 경합·암호화 전달·늦은 결과·회전/해제·기존 사용자 데이터 보존 검증이 그대로 통과한다. 테스트 DB/기본 사용자·시퀀스는 사례마다 독립이며 표식 검증을 우회하지 않는다. 측정상 불필요한 서버 시작은 5회에서 0회 또는 필요한 1회로 감소한다. setup/실행 실패에도 엔진 종료 후 DB를 삭제하고 잔여 DB/연결 0을 확인한다.
- 영향받는 상태·도구·노드: `tests/test_worker_postgres.py`, 필요한 `tests/conftest.py` DB 준비 연결. 제품 schema·migration·상태·도구·노드 없음.
- 섞지 않을 것: 세션 DB 하나의 데이터 공유, 이미 migration된 template으로 upgrade 검사 대체, 여러 연결 검사를 rollback 하나로 대체, SQLite·모의 벡터 대체, 운영 풀 상한 변경.
- 선행 작업: 1·2절과 상위 계획 3절/#219. 같은 conftest의 빌드/DB 변경을 순서대로 병합하고 기존 상위 #220의 선행 조건을 유지한다. #219의 완료 여부는 이 설계에서 미확인이다.
- 하는 사람: Codex.

이전 환경의 자체 서버 fixture 12~13초를 이번 환경의 확정 절감량으로 쓰지 않는다. tmpfs/디스크 차이가 크므로 현재 환경에서 비용이 유의미할 때만 적용한다. 업그레이드는 새 DB에 이전 스키마/가상 데이터를 직접 심고 실제 migration을 실행한다. 서버를 재사용하는 것과 migration 결과/가변 데이터를 공유하는 것은 다르다.

## 5. 독립 검사를 기존 8-worker 집합으로 이관

- 할 일: 1절 대응표를 읽고 실제 호출 자원별로 파일을 나눈다. `test_local_gmail.py`에서 실제 실행기 사례는 남기고 가짜 Google/독립 DB/인프로세스 API 사례를 별도 모듈로 검토한다. `test_knowledge.py`에서 실제 PageRenderer/Office 사례와 FakeRenderer·chunk/vector/독립 DB 사례를 분리한다. 설정 API와 브라우저 혼재, 4절 이후 worker PostgreSQL 모듈도 같은 방식으로 검토한다. 공통 가짜 helper는 `tests/fakes/`로 옮겨 test 모듈 간 import를 정리하고 검증된 새 모듈만 `tests/parallel.py` 목록에 추가한다.
- 완료 기준: 기존 node ID→새 node ID가 1:1 대응하고 parameter별 assertion/오류/권한/성찰 경로가 보존된다. `process_restart` 같은 함수 이름만으로 실제 OS 프로세스 여부를 판단하지 않는다. 8-worker/serial/정책 집합이 겹치지 않고 모든 기존 검증을 포함한다. 8 workers와 직렬 모두 통과하며 같은 데이터/파일/포트·환경·시간을 공유하지 않는다. 새 모듈/미분류의 기본 serial 정책도 유지한다.
- 영향받는 상태·도구·노드: 대상 테스트 파일·`tests/fakes/`·`tests/parallel.py` 분류 목록과 대응표. 제품 상태·도구·노드 없음.
- 섞지 않을 것: 실제 브라우저/Office/PC 실행기를 병렬 목록에 넣기, assertion 삭제/skip 추가, 사례를 합쳐 개별 실패 정보를 잃기, 8 workers 초과.
- 선행 작업: 2·4절. 빌드 fixture와 DB 경계를 먼저 확정하고 관련 파일의 변경을 합친다. 3절과는 파일/공통 기록 변경이 겹치지 않는 범위에서 병행 가능하다.
- 하는 사람: Codex.

기준 113건 전체가 자원 때문에 직렬이어야 하는 것은 아니다. 반대로 Mock 객체를 쓴다는 이유만으로 실제 렌더/서버/DB 전이 의존성까지 없다고 가정하지 않는다. 이동한 테스트 수는 절감 시간과 같지 않다. 병렬 단계 증가분까지 포함해 전체 시간을 비교한다. 사용자/계정별 가짜 공급자 객체와 호출 목록은 테스트마다 새로 만든다.

## 6. 전체 시간·동등성·자원 예산으로 채택 판정

- 할 일: 1절 기록 계약과 2~5절 결과를 읽고 변경 전후를 같은 측정 경계로 비교한다. 순차 단계와 전체 3단계 파이프라인을 각각 최소 3회 측정한다. commit·OS·Python/Node/브라우저/Office/pgvector 버전·캐시 준비·스토리지·CPU/메모리 상한을 동일하게 기록한다. 상위 #221의 반복 부하 검증에 결과를 연결한다.
- 완료 기준: 전체 검증의 대응표가 누락/중복 0이며 예상한 플랫폼 제외만 존재한다. 순차와 전체 중앙값이 모두 줄고, Linux/Windows 필수 검사가 통과하며, OOM·DB 충돌·공유 데이터 변경·잔여 프로세스/DB는 0이다. 순간 표본·컨테이너 수명 peak·단계별 프로세스 RSS를 구분한다. 한도가 넘거나 간헐 실패가 생기면 해당 최적화만 되돌린다.
- 영향받는 상태·도구·노드: 시험 기록·계획의 완료 표시·필요한 CI 결과 수집. 제품 상태·도구·노드 없음.
- 섞지 않을 것: 실패 재시도로 녹색 만들기, skip으로 사례 숨기기, 검사/Ruleset 완화, CPU/메모리 한도를 늘려 개선으로 표현하기, 운영 배포.
- 선행 작업: 2·3·4·5절의 채택 또는 미채택 결론이 모두 병합돼 있어야 한다.
- 하는 사람: Codex.

기존 환경 예산은 테스트 컨테이너 5GiB, DB 1.5GiB, 최대 8 workers였다. 새 기준 환경에 같은 예산을 적용하거나 변경 이유를 먼저 기록한다. 개선 전후 실행 순서를 바꾼 반복/동일 워밍업으로 캐시 순서 효과를 줄인다. 비용이 큰 비교 실행은 이 절에서 계획한 횟수만 수행하고, 일반 수정 중에는 관련 사례부터 확인한다. 최종 전체 검증은 생략하지 않는다.

## 작업 순서와 기존 계획 연결

- 1절 → 2절 → 상위 #219 → 4절 → 5절 → 6절이 기본 순서다. 3절은 1절 후 2·4·5절과 파일 충돌이 없는 범위에서 진행하고 6절 전에 병합한다.
- 1절은 상위 #217, 2절은 #218, 4절은 #220, 6절은 #221의 순차 단계 상세 작업이다. 상위 작업의 나머지 범위까지 끝났다고 표시하지 않는다. 새 하위 추적 Issue와 상위 Issue를 같은 구현 PR에 연결하고 같은 최적화를 중복 PR로 만들지 않는다.
- 상위 `test-speed-improvement.md`의 CI 계층 최적화(#219)와 이 설계의 테스트 내부 최적화를 구분한다. #219는 병합된 1·2절의 기록/fixture를 읽고 수행하며, 이 설계에서 그 완료를 가정하지 않는다. 4절의 DB 최적화는 기존 상위 계획대로 #219 병합 후 시작한다.
- 각 절은 별도 구현 PR이다. 효과가 없으면 성능 변경을 강행하지 않고 측정 결과와 미채택 결론으로 완료한다. 신규 제품 기능은 포함하지 않는다.
