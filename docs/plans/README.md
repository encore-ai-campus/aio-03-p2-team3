# 계획 파일 (docs/plans/)

기능이 둘 이상 섞인 요청(예: 도구 여럿 추가, 도구 추가와 그래프 구조 변경)은 바로 구현하지 않고, 이 폴더에 계획 파일을 만들어 PR로 먼저 올린다. 규칙 원문은 `.work/RULES.md` 7절이다. [Request]

## 순서
1. AI가 `docs/plans/<작업명>.md`만 만들어 PR로 올리고, 하위 작업마다 Issue를 만든다(RULES 7절 8번). 작업명은 영어 소문자·하이픈(브랜치 이름과 같은 방식). [Request · Past work: aio3]
2. 계획 PR을 병합한다.
3. 하위 작업마다 새 작업을 시작한다(Codex는 새 작업, 대화는 새 대화). 요청에 `docs/plans/<작업명>.md#N`을 적고, AI는 그 절만 읽고 그 절만 한다. 다른 하위 작업을 같은 작업의 후속 요청으로 잇지 않는다. 맡는 사람은 그 Issue의 Assignees에 자신을 넣고, 선행 작업이 병합된 절부터 시작한다. [Request · Claude proposal]
4. 하위 작업을 마치면 같은 PR에서 그 절 제목 끝에 `(완료)`를 붙인다. [Claude proposal]
5. 하위 작업 하나 = 기능 하나 = 작업 하나 = PR 하나다. PR 양식의 '관련 Issue·계획'에 `docs/plans/<작업명>.md#N`을 적는다. [Request]

## 형식
아래 틀을 복사해 쓴다. 하위 작업은 `## N. 제목` 절 하나씩이고, 절마다 여섯 줄을 모두 둔다. [Request · Past work: setup]

```markdown
# <작업명> 계획

- 목표: <이 계획을 마치면 무엇이 되는가>
- 관련 Issue: #번호 또는 없음
- 조율함: <공통 부분을 바꾸면 조율한 팀원, 없으면 "해당 없음">

## 1. <첫 하위 작업 제목>
- 할 일: <무엇을 만들거나 고치는가>
- 완료 기준: <확인할 수 있는 조건. 예: 정상·오류 요청 각 1개의 실제 결과>
- 영향받는 상태·도구·노드: <상태 필드, 도구 이름, 노드 이름. 없으면 "없음">
- 섞지 않을 것: <이 하위 작업에서 하지 않을 일>
- 선행 작업: <먼저 병합돼야 할 절 번호. 없으면 "없음">
- 하는 사람: <Codex / 사람(콘솔·계정 설정처럼 AI가 못 하는 일) / Claude>

## 2. <다음 하위 작업 제목>
- 할 일:
- 완료 기준:
- 영향받는 상태·도구·노드:
- 섞지 않을 것:
- 선행 작업:
- 하는 사람:
```

## 하위 작업끼리 맞출 것
- 서로 맞춰야 할 것(상태 필드 이름, 도구 입출력 형식)은 첫 하위 작업에서 정해 파일로 남기고, 뒤 하위 작업의 '할 일'에 그 파일을 읽으라고 적고 '선행 작업'에 첫 하위 작업 번호를 적는다. [Past work: setup · Claude proposal]
- 선행 작업이 없는 절끼리는 동시에 해도 되고, 같은 공통 부분을 고치는 절은 선행 작업으로 잇는다(RULES 7절 2번). [Request]
- 상태 객체·도구 스키마·그래프(공통 부분)를 바꾸는 하위 작업은 시작 전에 관련 팀원과 조율하고, 요청에 `조율함: <팀원>`을 적는다(`.work/TASK.md`). [Request · Claude proposal]
- 이 폴더의 작업에는 KB로 작업량을 재지 않고 `.work/FLOW.md`·`.work/STATUS.md`를 쓰지 않는다. KB 재기는 세팅 단계 작업에만 쓴다(RULES 7절 7번). [Request]
