## 11절 구현

- 회사·계좌·단가·PNG 이미지는 기존 `/api/trade/settings` API를 재사용한다.
- 거래처는 기존 `counterparties` 표에 `PUT /api/trade/settings/counterparties`만 추가했다. 회사명 정규화 키를 서버에서 만들고 본인 행만 갱신한다. 별칭은 20개까지이며 서버 소유권 필드는 입력으로 받지 않는다.
- 단가의 판매/매입 역할·통화·거래처 범위를 보존한다. 수량/금액을 브라우저에서 확정 계산하지 않는다.
- 저장 실패는 입력을 유지하고 성공 응답을 받은 뒤에만 저장 안내를 표시한다. 다른 레코드/파일을 선택하면 이전 저장 안내를 지운다.
- 회사 이미지는 Bearer 다운로드로 미리 보고 조회 취소·객체 URL 정리를 한다. 새 이미지/설정이 기존 검토·발급 파일을 바꾸지 않는다.
- React/JavaScript/Vite와 기본 폼/CSS를 사용했다. 새 런타임 패키지·폼 라이브러리·상태관리 도구는 추가하지 않았다.

## 12절 구현

- 문서 종류 선택에서 `/app/trade/pi`로 이동한다. 초안을 저장하면 ID가 포함된 주소로 바뀌어 새로고침·재로그인 후 재개할 수 있다.
- 직접 입력/AI 추출·수정·누락 보완·검토 제안·승인/취소/수정·PDF/XLSX 다운로드는 기존 문서 API와 계산/가격 규칙을 사용한다. 수량/금액은 문자열이며 브라우저에서 확정 계산하지 않는다.
- 검토에는 고정된 문서·회사·계좌·직인/로고·revision·해시·파일 형식을 표시한다. 이미지 조회 API만 추가해 소유자·종류·문서 ID·제안 범위를 검사하고, Storage의 보관된 이미지를 해시 검증해 private/no-store로 반환한다. 조회로 파일을 발급하지 않는다.
- 개인 OpenAI 키 등록/삭제는 기존 암호화 서비스를 Bearer 전용 `/api/openai-key`로 연결했다. 키를 응답/오류에 되돌리지 않고, 서버 저장 방식/로컬 환경 파일 방식은 기존 계약을 유지한다. 실행 방식 선택이나 PC 장치 연결 화면을 새로 만들지 않았다.
- 저장/다운로드 실패와 409는 입력을 보존하고, 최신본을 다시 읽으면 입력이 바뀜을 안내한다. 승인/저장 중복 클릭을 막고 서버 응답 후 상태를 바꾼다. 같은 사용자 토큰 갱신은 저장 전 입력을 다시 읽지 않는다. 다른 문서로 이동할 때 조회/요청을 취소해 늦은 응답을 버린다.
- 상품/통화/거래처/단위가 바뀌면 단가 확인을 해제한다. 직접 입력한 단가(0원 샘플 포함)는 명시적 확인 뒤 적용하고, 확인하지 않으면 서버의 기존 단가표 재확인 규칙을 따른다. 새 패키지·범용 채팅/폼 엔진은 추가하지 않았다.

## 남은 검증

macOS의 과거 개인 PC 모의 시험 1개는 Gmail 후보 완료 시간 초과가 남아 있다. 이후 PR #166의 Windows 실행기 검사는 통과했지만 macOS 문제나 실제 사용자 PC 연결의 완료 근거로 대신하지 않는다. 두 CI 실패를 고친 뒤 최신 브랜치 전체 통과는 아직 미확인이다. 설정/PI의 표적 검사와 운영 연결은 별도로 구분한다.

환경변수 설정 후 실제 Supabase 로그인·비공개 버킷·OAuth 연결 확인이 필요하다. 값은 저장소/채팅에 넣지 않는다. Supabase는 루트 `.env` 한 곳의 `SUPABASE_URL`·`SUPABASE_PUBLISHABLE_KEY`·`SUPABASE_SECRET_KEY` 세 값으로 설정한다. 버킷은 기본 `trade-files`를 쓰며 `DATABASE_URL`과 기존 Google/암호화 설정은 별도 서버 설정이다. Vite는 URL·공개 키만 브라우저에 전달하고 `frontend/.env`는 읽지 않는다. `FRONTEND_PORT`는 개발 포트이며 비우면 5174, 지정하면 그 번호만 사용한다. 사용자 PC의 루트 `.env`에는 3000을 지정했다. `npm run check:env`는 기본/지정/잘못된 포트 처리와 가짜 값의 공개 범위/서버 비밀값 빌드 제외를 확인해 통과했다. lint·규칙 검사도 통과했고 설정 변경만 확인했으므로 전체 pytest는 반복하지 않았다.

## 2026-11-13 로컬 로그인 설정 확인

- 실행 중인 프론트가 `/dashboard/project/...` 관리 URL을 Supabase API 주소로 전달해 404로 이동했다. 루트 `.env`는 프로젝트 API 주소였지만 실행 중 환경값은 이전 주소여서, 이전 프로세스를 종료하고 두 공개 환경값을 제거한 실행 환경에서 다시 시작했다. 저장소에는 실제 URL·키를 기록하지 않는다.

### 현재 기능을 실행하는 방법

1. 루트 `.env`에 기본 `AI_RUNTIME=server`, PostgreSQL `DATABASE_URL`, Supabase URL/공개 키/서버 비밀 키와 기존 Google/암호화/세션 설정을 준비한다. Supabase Google 공급자·실제 개발 포트의 `/app/login` 반환 주소와 비공개 Storage 버킷도 필요하다. 실제 값은 채팅·PR에 남기지 않는다.
2. 레포 루트에서 `uv sync --locked` 후 `uv run uvicorn app.main:app --reload`로 백엔드 8000을 실행한다.
3. 다른 터미널에서 `cd frontend`, `npm ci`, `npm run dev`를 실행한다. 기본 주소 `http://localhost:5174/app/`에서 로그인하고 설정→PI 작성을 사용한다. `FRONTEND_PORT`를 지정했으면 그 포트로 접속한다. `/api`는 Vite가 8000으로 프록시한다.
4. 수동 PI 작성·검토·파일 발급은 AI 키 없이 가능하다. AI 추출/메일 분석은 본인 계정의 키 등록 또는 기존 개인 PC 실행기 연결이 필요하다. 파일 발급에는 실제 Storage·회사/계좌/직인 등 업무 조건도 충족해야 한다. PO·CI·PL은 현재 API만 있고 React 화면은 없다.

### 과제 기준의 통합 완료 조건과 우선순위

- 최소 대표 흐름은 **화면 → 메일 StateGraph → 조건별 도구 선택 → 누락 질문/문서 생성 → 성찰·재검증 → 결과 확인 → 사용자 승인**으로 정할 수 있다. 문서 확정/파일 발급과 Gmail 발송 승인은 계속 구분한다. 별도 마스터 챗봇이나 네 개의 독립 에이전트는 과제 필수 조건이 아니다.
- 현재 계획대로라면 13~20절을 순서대로 연결하고 21절에서 React 배포, 22절에서 실제 데이터/운영 전환을 확인한다. 배포를 마지막에 둔 순서 때문에 개발 화면 완료가 배포 화면 노출로 이어지지 않는다. **PI를 먼저 운영에서 확인하려면** 21절의 최소 빌드/제공 작업을 앞당기는 계획 조정이 필요하다. 이번 검토에서 선행 작업을 변경하거나 운영 설정을 바꾸지는 않았다.
- 19절의 검증에는 무역 후보의 문서 종류/ID 전달, 같은 소유자의 문서 재개, 누락 보완, CI 원본/PL 합계 확인, 문서 revision 고정, 명시적 발송 승인과 중복/불명확 오류 처리를 포함해야 한다. 기존 메일 발송 서비스는 `ready`·후보/문서의 같은 thread/run을 확인하므로 독립 API로 `issued`가 된 문서를 그대로 보낼 수 있다고 가정하지 않는다.
- 실제 공유 URL에서 정상 요청·정보 부족·도구 실패·판단 오류 수정과 결과 재접속을 확인하고, 성찰 끔/켬의 완료율·도구 선택 정확도·일관성·평균 재시행 횟수를 기록해야 R-12~R-14의 완료 근거가 된다. 모의 시험 통과는 실제 API/배포 완주의 근거를 대신하지 않는다.

## 12절 코드 검토

### Standards

문서화된 규칙 위반과 수정이 필요한 과설계 지적은 없었다. 기존 React/FastAPI/키 서비스를 재사용하고 검토 이미지 고정/소유권 계약을 유지했다. 별도 정확성 문제로 수량 두 입력의 우선순위 충돌 1건을 전달받았다.

### Spec

계획의 입력 보완/수정 경로에서 3건을 발견했다. 일반 품목/프로모션에서 quantity와 paid_quantity의 별도 수정이 서버 우선순위에 덮이는 문제, 추출된 seller를 편집할 수 없는 문제, null 상품군이 기타로 보이는 문제였다. 유상 수량 입력을 하나로 합쳐 두 원본 필드를 함께 갱신하고 프로모션 무상 수량은 읽기만 허용했다. 판매자/구매자 등록 정보까지 편집하고, 미확인 상품군은 별도 선택 안내로 표시한다. 샘플에서 적용하지 않는 프로모션/할인/무상 입력도 비활성화했다.

최초 결과: Standards 규칙/과설계 0건(별도 정확성 후보 1건), Spec 3건. Spec의 가장 큰 문제였던 조용한 수량 유실을 포함해 세 경로를 수정했고 위 브라우저 표적 확인을 통과했다. 검토자는 추가 테스트를 실행하지 않았다.
