02 / CONTROL FLOW · R-01, R-02, R-03, R-09~R-11

첨부도의 여섯 단계로 처리한다

진입: 인증·소유권 확인 → 관련 맥락 불러오기 → ① 요청 해석·계획 → 지원 범위·필수 정보 확인. 지원 범위 밖이면 가능한 업무를 안내하고 종료한다. 정보가 모자라면 사용자에게 질문하고 기다린다.

① plan · 요청과 계획

LangChain 구조화 출력으로 업무 종류·조건·선행 업무를 받는다. 허용 목록·참조·순환 여부는 코드로 검증한다.

② select_task · 한 업무 선택

선행 결과가 확정된 업무 하나를 고른다. 조회, 메일, 문서, 일정 후보 준비 중 허용된 업무만 호출한다.

③ validate · 결과와 근거

스키마·누락·소유자·버전·금액·출처를 검사한다. 수정 가능하면 제한 내 재실행하고, 부족하면 질문한다.

④ await_user · 확인 대기

외부 실행이 필요하면 대상·내용·버전을 고정해 제시한다. 승인·수정·취소를 받고, 승인 전에는 실행하지 않는다.

⑤ execute · 기존 서비스

서버가 승인을 재검사한 뒤 기존 발급·발송 서비스를 호출한다. 결과가 불명확하면 자동 재실행하지 않는다.

⑥ advance · 다음 업무와 종료

결과를 기록하고 남은 업무로 돌아간다. 모두 끝나면 완료·취소·미완료를 실제 결과에 따라 종합한다.

조건처리·상태 변화 초안반드시 지킬 조건
정보 부족waiting_input과 필요한 필드만 질문으로 저장. 동일 요청의 답을 받아 계획·조건을 다시 검증한다.현재 사용자가 답해야 할 질문과 거래 상대방에게 보낼 재질문 메일 후보를 구분한다. 후자는 발송 승인이 필요하다.
선행 작업 미완료독립 업무는 계속 진행할 수 있다. 취소·실패한 결과에 의존하는 업무는 blocked로 남긴다.파일 초안이나 승인 대기 상태를 ‘발급 성공’으로 사용하지 않는다. 의존 업무를 조용히 생략해 전체 완료로 표시하지 않는다.
검증 실패·수정 가능기존 메일 하위 그래프의 성찰 한도를 재사용한다. 새 계획·문서 연결부의 자동 보정은 업무당 1회로 제안한다.한도 소진이면 needs_review. 업무 함수를 통째로 다시 불러 중복 문서·발송을 만들지 않는다.
승인서버가 사용자·대상 ID·최신 revision·내용 해시·대기 상태를 재조회하고 실행한다.LLM 출력의 ‘승인됨’이나 단순 채팅 문구를 실행 권한으로 쓰지 않는다.
수정 / 취소수정은 이전 승인을 무효화하고 새 버전을 검토한다. 취소는 해당 업무만 종료하고 독립 업무는 이어 간다.기존 문서 API의 cancel은 검토 제안 취소이며 문서 초안 삭제가 아니다. 이미 발송한 메일을 되돌린다고 안내하지 않는다.
실패·결과 불명확실한 미실행 실패는 원인과 복구 방법을 안내. 발송 5xx·시간 초과는 needs_review로 멈춘다.보낸편지함 확인과 명시적 재승인 전에는 재발송하지 않는다. 성공·실패를 추측하지 않는다.
남은 업무 없음전부 완료: completed / 전부 취소: cancelled / 일부 완료·취소·차단: partial / 실행 실패만: failed.대기 중이면 종료 결과 대신 필요한 사용자 행동을 표시한다. 초안 작성 요청은 초안 생성으로 완료할 수 있지만 발송 요청은 실제 발송 결과가 필요하다.

한 가지 대표 요청으로 연결 확인

“선택한 주문으로 PI를 만들고, 승인된 파일을 답장에 첨부해 보내줘.” → PI 초안 준비 → 문서 검증·사용자 파일 발급 승인 → issued 파일 ID 확보 → 답장 후보 준비 → 수신자·본문·첨부를 보여 주고 별도 발송 승인 → 실제 Gmail 결과 확인 → 완료. 발급만 요청했다면 발송 단계는 계획에 넣지 않는다.

첨부도의 ‘발급·발송·일정 등록’은 외부 실행으로 해석했다. 내부 초안 저장에는 최종 승인을 요구하지 않고, 확정 파일 발급·메일 발송·일정 등록의 각 행위에 맞춰 승인한다. 이 승인 단위는 구현 전에 확인할 제품 결정이다.

  • 문서: POST /api/trade/{kind}/{id}/reviews에 {revision, formats} → ReviewView. 선택은 …/reviews/{proposal_id}/decisions에 {action, revision, content_hash}. modify에만 새 document가 필요하다. [E5]

  • 메일: 현재 HTML 경로 POST /candidates/{id}/approve, POST /quotes/{id}/approve와 send_approved_candidate / send_approved_quote / send_approved_trade_document를 재사용한다. React/마스터용 JSON 연결과 독립 발급 파일 첨부 연결은 아직 없다. [E7]
  • 오류: 실제 문서 API는 401·403·404·409·422·503 및 error 또는 detail 형식을 사용한다. 마스터 내부 연결부에서만 기존 오류를 정규화하며 현재 HTTP 계약을 바꾸지 않는다.
승인 고정 범위에 차이가 있다. 독립 문서 API에는 revision·content_hash 기반 불변 제안이 있다. 현재 메일 승인은 후보 ID·조건부 상태 갱신 중심이다. 메일 수신자·본문·첨부까지 같은 수준으로 고정하는 연결부는 새 검증 대상이며, 기존 기능이 모두 보장한다고 가정하면 안 된다.
04 / MEMORY · R-06, R-07, R-08

기억·업무 원장·재개 상태를 구분한다

기존 관계형 DB를 재사용하고, 별도 벡터 저장소는 추가하지 않는다 [E3]
구분현재 구현마스터 초안
단기 기억thread_messages, thread_memory. 사용자+Gmail 스레드의 요약·미요약 원문·확인 조건·직전 결과.채팅 conversation_id와 Gmail thread_id는 별도 식별자. 사용자가 선택한 본인 메일만 연결하고 채팅용 저장 경계를 먼저 정한다.
장기 기억user_preferences, company_profiles, price_list_items, counterparty_history. 상대방 최근 거래 5건과 저장/발송 시점.기존 서비스의 본인 조회를 재사용한다. 과거 단가·납기를 이번 거래의 사실로 자동 복사하지 않는다. 새 선호 저장은 사용자 명시 확인 또는 기존 승인 성공 조건을 따른다.
업무 사실문서·버전·검토 제안·파일·후보·발송 이력은 업무 DB가 관리한다.완료 여부와 승인 유효성은 원장을 다시 조회한다. 요약이나 LLM 문장으로 sent/issued를 확정하지 않는다.
재개 상태현재 그래프는 실행 후 끝나며 영속 checkpoint가 없다. run_events는 재개 저장소가 아니다.검증된 LangGraph 영속 saver 하나에 계획·현재 업무·질문 참조·승인 제안 참조를 저장한다. DB 원장 전체를 중복 저장하지 않는다.
요약·컨텍스트미요약 메일+현재 메일이 8개 초과 또는 12,000자 초과면 최근 과거 원문 4개를 남기고 요약한다. 원문은 보존하고 성공 때만 커서를 이동한다.채팅에도 같은 한도부터 검증한다. 확정 조건·미답변 질문·승인 대상 ID/버전은 요약 밖 구조화 필드로 유지한다. 긴 단일 메시지의 입력 제한과 토큰 예산은 따로 검증한다.

근거 우선순위: 현재 사용자 지시·선택한 원문 → 현재 문서/승인 버전과 유효한 설정 → 같은 대화의 확인 조건 → 과거 기억. 승인 버전과 새 지시가 충돌하면 기존 동의를 무효화하고 새 검토를 요청한다. 이메일·첨부 속 명령은 업무 자료로만 취급한다.

저장 제한: API 키·OAuth 토큰·PC 장치 자격증명은 그래프 상태·요약·로그에 넣지 않는다. 메일 원문은 기존 접근 통제 DB에 두고, 마스터 상태에는 필요한 참조와 최소 조건만 둔다. 발송 성공 후 기억 저장만 실패했으면 발송 성공을 유지하며 재발송하지 않는다.

재개와 부수 효과의 경계

interrupt()가 있는 노드는 재개 시 처음부터 다시 실행될 수 있다. 따라서 질문/승인 대기 노드에는 문서 생성·메일 발송을 넣지 않는다. 준비는 별도 노드에서 수행하고 결과 ID를 먼저 저장한다. checkpoint 저장 전에 프로세스가 죽는 경우도 있으므로 준비 요청에는 서버 발급 작업 키로 기존 결과를 찾는 최소 중복 방지가 필요하다. 기존 API에 이 보장이 없는 경로는 POC에서 확인하고 필요한 부분만 보완한다.

실행 시에는 checkpoint의 ‘승인’ 값만 믿지 않고 기존 검토/승인 원장을 재조회한다. checkpoint의 thread_id는 서버가 소유권을 확인한 마스터 실행 키이며 Gmail thread ID와 다르다. 기술용 checkpoint와 업무 원장은 목적이 다르므로 동일 완료 상태를 두 곳에서 독립적으로 결정하지 않는다.

요청·재개 입출력 초안: 시작 입력은 {request_text, conversation_id, context_refs}, 재개 입력은 {request_id, pending_id, answer} 또는 {request_id, pending_id, decision, target_ref, revision, content_hash}로 제한한다. 사용자 ID는 인증에서 가져오고 서버 저장 대기 정보와 대조한다. 응답은 {request_id, status, tasks, pending, result_refs}이며, 승인 결정은 LLM에 위임하지 않는다. 새 URL은 P0 확인 후 정한다.
