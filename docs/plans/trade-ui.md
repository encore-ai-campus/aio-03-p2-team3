## 설계: 구현 방식

검토한 방식은 독립 React UI와 기존 FastAPI/Jinja 화면 확장이다. 사용자가 기존 API 연결 방향에 맞는 독립 React UI를 선택했다. React는 표 편집·문서별 입력·검토 상태를 재사용하기 좋고 프런트엔드 빌드 관리가 추가된다. 템플릿 확장은 배포가 간단하지만 사용자가 선택한 방향과 달라 채택하지 않는다.

- 제안 기술: `frontend/`의 React + TypeScript + Vite SPA. UI 구성은 Radix Themes 한 가지와 프로젝트 CSS 토큰으로 통일한다. 실제 패키지 버전은 1절 구현 시 공식 배포 정보로 확인해 고정하고 lock 파일을 커밋한다.
- 연결: 기존 `/api/session`, `/api/trade/{pi|po|ci|pl}`, `/api/trade/settings`, `/api/trade/files/{id}`를 호출한다. API 필드·오류 원본은 `docs/trade-api.md`와 FastAPI OpenAPI다.
- 개발: Vite에서 `/api`, `/login`, `/auth`, `/inbox`, 로그인 화면의 `/static` 및 `/logout`을 FastAPI로 프록시한다. 현재 OAuth callback은 `/inbox`로 복귀한다. 로그인은 별도 탭에서 진행하고 원래 React 탭으로 돌아와 세션을 다시 확인한다. 로그인 성공 뒤 별도 토큰을 발급하지 않고 기존 세션 쿠키를 쓴다. 자동 복귀를 위한 auth 라우터 변경은 하지 않는다.
- 운영 제안: FastAPI와 같은 출처의 `/trade/` 아래에 React 빌드 결과를 제공한다. API와 기존 Gmail 화면은 기존 주소를 유지한다. 별도 Sites 호스팅·새 인증 서버는 만들지 않는다.
- 빌드 전에는 `/trade`를 비활성화하거나 명확한 안내로 처리한다. SPA fallback은 `/trade/` 범위에만 적용하고 없는 API·파일 경로를 HTML로 바꾸지 않는다.
- 서버 데이터는 API 응답을 원본으로 삼는다. 금액·수량은 문자열로 편집·전송하며 `Number`/`parseFloat`로 계산하지 않는다. 합계·가격 인증·승인 상태는 서버에서만 확정한다.
- 인증: `credentials: 'include'`와 세션 CSRF 토큰을 사용한다. 401이면 원래 탭의 메모리 초안을 유지하고 별도 탭 로그인 링크와 ‘로그인 완료 후 다시 확인’ 버튼을 제공한다. 복귀 시 `/api/session`을 다시 읽고 사용자 ID가 달라졌으면 이전 사용자의 초안·캐시를 지운다. 403이면 토큰 재조회와 사용자 재시도 안내를 한다. 승인 등 변경 요청은 자동 재전송하지 않는다. 새로고침·탭 닫기에는 초안이 보존되지 않음을 안내한다.

## 설계: 화면과 사용 흐름

업무용 밝은 테마를 기본으로 한다. 밝은 회색 작업 배경, 흰 입력 영역, 짙은 파란색 주요 동작, 차분한 구분선과 일정한 모서리를 사용한다. 한국어 본문과 숫자가 읽히는 시스템 글꼴을 쓰고 금액 열은 오른쪽 정렬한다. 장식 이미지·대형 소개 영역을 넣지 않는다.

```text
┌ 문서 작업 공간 ─────────────────────── 계정 / Gmail로 이동 ┐
│ PI 인보이스 │ 문서 종류 · 제목                  새 문서 작성 │
│ PO 발주서   │ 목록: 번호 / 종류 / 상태 / 통화 / 합계          │
│ CI 상업송장 │                                                │
│ PL 포장명세 │ 편집: 기본 정보 · 거래처 · 품목 표               │
│            │ 검토: 거래 내용 요약 · 누락 항목 · 서버 계산 합계  │
│ 회사 설정  │                       저장 / 검토 / 승인·발급    │
└────────────┴────────────────────────────────────────────────┘
```

- 목록: 문서 종류 탭, 최근 문서, 로딩·빈 목록·실패 재시도. 서버가 반환한 최근 50건 안에서 검색·상태 필터를 적용한다고 표시한다. 전체 기록 검색/서버 페이지네이션을 제공하는 것처럼 표시하지 않는다.
- 작성: 직접 입력과 문장으로 시작을 선택한다. AI 추출 결과는 저장된 초안으로 열어 사용자가 사실·누락·가격을 확인한다. 추출 중 중복 클릭을 막고 성공 전 자동 재요청하지 않는다.
- 편집: 기본 정보·당사자·문서별 항목을 한국어 라벨로 제공한다. 품목 행 추가/삭제와 샘플 표시, 입력 근거·누락 안내를 제공한다. JSON 입력칸을 일반 업무 화면으로 사용하지 않는다.
- 검토: 저장된 버전의 내용을 읽기 전용으로 보여준다. 클라이언트의 편집 중 값으로 승인하지 않는다. API에 승인 전 PDF 미리보기 경로가 없으므로 PDF가 미리 생성된 것처럼 보이지 않고 HTML 요약으로 검토한다.
- 승인: `revision`·`proposal_id`·`content_hash`를 서버 응답 그대로 사용한다. 승인/취소/수정은 별도 동작이다. 승인 성공 뒤에만 서버가 반환한 PDF/XLSX 다운로드를 노출한다. 버튼 설명은 파일 발급이며 Gmail 발송이 아님을 알린다.
- 수정: 저장 후 이전 검토 제안은 재사용하지 않는다. 기존 발급 파일은 과거 버전으로 구분한다. 409는 최신 문서 확인과 변경 비교를 안내하며 자동 덮어쓰기를 하지 않는다.
- 반응형: 넓은 화면은 좌측 메뉴+본문, 좁은 화면은 메뉴 접기+세로 폼을 사용한다. 품목 표만 가로 스크롤한다. 키보드 이동, 입력 라벨, 오류 요약 링크, 포커스 이동, 상태의 텍스트 표현을 제공한다.
- 사용자 입력은 React 텍스트로 출력한다. 입력 원문을 HTML로 삽입하지 않는다. 주문 본문·계좌·직인·CSRF 토큰을 브라우저 로그나 장기 localStorage에 저장하지 않는다. 화면 전환 시 미저장 입력 경고와 종류별 메모리 내 초안을 제공한다.

## 설계: API에 맞춘 문서별 차이

| 영역 | 화면에서 제공할 기능 | 기존 백엔드 제약 |
|---|---|---|
| PI | 판매 문서 입력, 샘플 행, 가격 변경 명시 확인, 통화별 계좌 | 계좌 6항목과 회사 직인 등 필수 설정 확인 |
| PO | 구매자/공급처 구분, 매입 단가·행사·할인 입력 | PI 판매 단가·은행 정보를 복사하지 않음 |
| CI | 현재 상태가 issued인 PI 선택과 버전 확인, 선적·원산지 등 편집 | 거래처·품목·통화·가격은 선택한 PI 버전에서 가져옴 |
| PL | 포장 행, 단위별 합계·원본 비교, 합계 승인/취소 | 포장 합계 승인과 최종 파일 발급 승인은 별개 |
| 설정 | 회사, 통화별 계좌, 단가 추가/갱신, PNG 로고·직인 | 현재 없는 단가 삭제·거래처 CRUD·이미지 원본 조회 API를 UI에 가짜로 만들지 않음 |

## 설계: 포함하지 않을 것과 알려진 한계

- 이미지/PDF OCR, 첨부 파일에서 PI 가져오기, 계약서, 마스터 챗봇, 자동 메일 발송, 신규 LLM/API 공급자 추가는 제외한다.
- PI의 과거 승인 버전 목록 API가 없으므로 최초 CI 화면은 현재 `issued`인 PI의 현재 revision만 선택한다. 과거 승인 버전 선택·과거 발급 이력 전체 탐색은 별도 API 보완 대상이다. 현재 문서 상세가 반환하는 발급 파일만 노출한다.
- 목록 응답에 거래처가 없어 거래처 정보는 상세 화면에서 제공한다. 목록 표시를 위해 문서마다 추가 조회하지 않는다.
- 앞선 검토에서 같은 상품명·다른 용량/SKU의 단가가 덮어써지는 문제가 재현됐다. 현재 가격 저장 API의 식별 키와 카탈로그 구성에 관한 별도 백엔드 수정 대상이다. 이 계획에서는 자동으로 고치지 않는다.
- 설정 UI에서는 현재 추가/갱신 기준(상품명·역할·통화·거래처)을 설명하고, 기존 항목을 갱신하기 전 현재 용량/상품코드와 바뀔 값을 확인한다. 별도 SKU를 함께 저장할 수 있는 것처럼 안내하지 않는다. 실제 동시 지원은 백엔드 수정 후 별도 검증한다.
- 같은 출처 서빙을 우선해 OAuth·쿠키·CORS 변경을 줄인다. 운영 Render 빌드 명령 변경은 7절에서 구체 변경과 검증 후 반영한다.
- 원래 작업 폴더의 `.env.example` 삭제와 비교용 `AI AGENTS/` 파일은 이 계획과 섞지 않는다. 깨끗한 최신 main의 분리 작업 공간에서 검사한다.

## 1. React 문서 목록과 세션 연결
- 할 일: 이 설계와 `docs/trade-api.md`를 기준으로 `frontend/`에 React/TypeScript/Vite를 준비한다. `/trade/` 기본 경로, 공통 레이아웃·접근성 토큰·API 클라이언트·정확한 문자열 숫자 타입·세션/CSRF 처리를 정한다. 문서 종류별 실제 목록을 조회한다. 로그인 시작/반환 경로를 현재 auth 코드로 확인한다. 공통 컴포넌트·API 타입·오류 처리 규칙은 `frontend/README.md`에 남긴다. 파일 지도에 `frontend/`를 등록한다.
- 완료 기준: Node 의존성 버전/lock 고정, 타입 검사와 production 빌드 통과. 가짜 API로 종류 전환·최근 50건 범위·로딩/빈 목록/실패·401·CSRF 처리를 확인한다. 실제 FastAPI 테스트 세션으로 목록 조회까지 브라우저 검증한다. 브라우저 주소에 문서 종류가 보이고 새로고침·뒤로가기가 동작한다.
- 영향받는 상태·도구·노드: 화면의 선택 문서 종류·세션·CSRF·목록 상태. 기존 AgentState·도구·노드는 변경하지 않는다.
- 섞지 않을 것: 문서 편집·승인, 설정 저장, 운영 배포, 백엔드 상품 식별 수정.

## 2. 회사·계좌·단가·이미지 설정 화면

- 영향받는 상태·도구·노드: 사용자 회사·계좌·단가표·브랜딩 설정 API. 그래프 상태·도구·노드는 변경하지 않는다.
- 섞지 않을 것: 가격 식별 키/DB 제약 변경, 거래처 CRUD API 신설, 문서 발급 UI.

## 3. PI 작성·편집·검토·파일 발급 화면

- 완료 기준: 가짜 AI와 실제 테스트 DB/API로 수량 0·샘플 0원·가격 변경 확인·계좌 누락·오래된 revision·중복 승인·파일 생성 실패를 검증한다. 브라우저에서 직접/AI 작성→수정→검토→발급→PDF/XLSX 다운로드가 가능하고 파일 내용과 화면 합계가 일치한다. 취소 후 발급하지 않고 수정 후 재검토한다.

- 섞지 않을 것: PO/CI/PL 입력, 첨부 추출, 메일 발송, 가격 정책 변경.

## 검증과 진행 규칙

- 계획 PR 병합 뒤 1절부터 새 작업으로 진행한다. 하위 작업 하나당 PR 하나이며 담당·선행 작업 완료는 Issue/PR로 확인한다.
- 각 구현 PR에서 바뀐 영역의 PROJECT_CONTEXT 절을 갱신하고 `python3 .work/check.py`와 `uv run pytest`를 직접 실행한다. Windows에서 `python3` 실행 파일이 없으면 같은 Python 스크립트를 `uv run python .work/check.py`로 실행하고 결과에 대체 명령을 명시한다.
- 프런트엔드 구현 PR은 타입 검사·production 빌드와 변경 기능에 맞는 의미 있는 테스트를 추가한다. 승인·정밀 숫자·오래된 버전·소유자 격리·화면 오류 처리를 우선 검증한다.
- 실제 API/OAuth/Render 시연은 가상 거래 자료로 수행한다. 가짜 AI 시험과 실제 API 시험을 구분한다.
- 4·5·6절은 공통 컴포넌트 변경이 겹칠 수 있으므로 담당자는 수정 범위를 조율한다. 같은 공통 파일 수정이 필요하면 먼저 병합한 뒤 나머지를 최신 main에 맞춘다.
