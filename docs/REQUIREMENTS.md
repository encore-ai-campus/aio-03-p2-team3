## 0. 이 문서를 받은 LLM의 작업 원칙

1. 아래의 **[필수 구현]**, **[필수 제출]**, **[필수 검증/운영]** 항목은 구현 및 완료 점검의 기준으로 사용한다.
2. **[예시/선택]**과 **[미지정]**을 필수 조건으로 바꾸지 않는다. 원문에 없는 기술, 제품, 수치, 구현 방식, API 개수를 과제 요구사항이라고 주장하지 않는다.
3. 설계·구현에 영향을 주는 불명확한 정보(선정 주제, 이용할 실제 API, 데이터 저장 서비스, 팀이 정할 정책 등)는 **추측해 결정하지 말고 사용자에게 확인을 요청한 뒤 진행한다.**
4. 실제 실행하지 않은 기능을 '완료', 측정하지 않은 수치를 '측정 완료'라고 표시하지 않는다. 실행 불가한 조건과 미검증 상태는 명시한다.
5. 프로젝트 범위가 바뀌더라도 공통 기술 요건(LangGraph 다중 도구 선택, 순환 흐름, 기억/컨텍스트 관리, 자가 성찰/피드백, 실제 API, 시험, 배포)을 유지한다.
6. 아키텍처 설계서·코드·실행 기록·시험 보고서·발표의 설명이 서로 일치하게 유지한다.

## 1. 프로젝트의 목적과 기본 서비스 흐름

**목표:** 도구와 기억을 이용해 사용자 문제를 해결하고, 판단 오류를 발견해 스스로 수정하는 에이전트를 개발한다. 실제 API를 사용하고, 수정 전후의 성능을 비교한 후 사용 가능한 서비스를 배포한다.

**대표 서비스 흐름:**

`사용자 요청 → 입력 및 기억 확인 → 도구 선택·호출 → 결과에 따른 판단 → 오류 감지·수정·재실행 → 검증된 결과 안내`

- 정상 완료뿐 아니라 **추가 질문**, **재실행**, **대체 경로(Fallback)**, **실패/종료 조건**도 설명 및 시험 가능해야 한다.
- 원문은 노드·도구의 수가 많은 것보다 **선택 이유, 상태 변화, 오류 수정 결과를 검증할 수 있는지**를 중요하게 다룬다.

| R-03 | [필수 구현] | 사용자 요청 조건 확인 및 누락 정보 처리 | 정보가 부족할 때 필요한 추가 질문 또는 적절한 경로로 진행 |
| R-04 | [필수 구현] | **실제 외부 API 데이터**를 의사결정에 사용 | 실제 API를 호출하는 정상·오류 시나리오와 결과 확인 가능 |
| R-05 | [필수 구현] | 그래프 **상태(State)** 설계 및 노드 간 전달 | 메시지, 입력 조건, 도구 결과, 오류, 반복 횟수 등 필요한 정보가 전이·갱신됨 |
| R-06 | [필수 구현] | **단기 기억(Session)** 연동 | 같은 대화의 조건, 앞선 질의와 결과를 후속 요청에서 활용 |
| R-07 | [필수 구현] | **장기 기억(Long-term Memory)** 연동 | 확인된 사용자 선호·과거 기록을 이후 대화에서도 활용 |
| R-08 | [필수 구현] | **컨텍스트 윈도우 관리 및 요약(Summarization) 전략** 적용 | 어떤 정보를 모델에 전달하고 언제/무엇을 요약하는지 정해져 있음 |
| R-09 | [필수 구현] | **자가 성찰(Self-Reflection)**에 의한 판단 오류 감지와 원인 분석 | 오류 유형별 판정 기준과 실제 감지 기록 존재 |
| R-10 | [필수 구현] | **피드백 루프**: 수정 전략 선택 → 재실행 → 재검증 | 수정 내용이 상태·입력·호출에 반영되고 결과가 다시 검증됨 |
| R-11 | [필수 구현] | 재시도 한도, 종료 조건, 대체 경로(Fallback) | 무한 반복 방지, 정상·실패·추가 질문 시 종료/전이 정의 |
| R-12 | [필수 검증] | 실제 API 기반 정상 및 오류 시나리오 실행 | 입력, 도구 실행, 상태 전이, 오류 및 최종 결과 기록 |
| R-13 | [필수 검증] | 자가 성찰 **적용 전후**의 성능을 같은 기준으로 비교 | 4개 필수 지표의 정의·측정값·실제 사례를 시험 보고서에 제시 |
| R-14 | [필수 구현] | 타인이 체험할 수 있는 사용자 화면과 서비스 배포 | 외부에서 접근 가능한 화면에서 대표 요청이 백엔드·도구를 거쳐 완료됨 |

### 상태·기억·컨텍스트 설계에 포함할 내용

- **그래프 상태:** 필요한 필드 각각에 대해 이름, 의미, 자료형, 초기값, 읽기/갱신 노드를 기록. `messages`, `tools_called`, `error_count`, `iteration`은 **예시 필드명이지 필수 고정 스키마가 아님**.
- **단기 기억:** 현재 세션의 메시지, 확인 조건, 직전 결과 등 유지 범위.
- **장기 기억:** 이후 세션에서도 활용할 확인된 사용자 선호, 과거 기록 등.
- **기억 우선순위:** 사용자/세션 구분, 저장·조회 시점, 현재 요청 조건과 과거 기억이 충돌할 때 적용 순서 명시.
- **컨텍스트:** 모델 입력에 포함할 메시지·기억·도구 결과 선택 기준, 길이 관리, 요약 시점, 요약에서 보존할 조건과 근거.
- **오류·종료:** 오류를 표시할 상태, 수정 전략, 반복 제한, 정상/실패/추가 질문 종료 조건.
- **시점 관리:** 과거에 조회한 날씨·행사 등 외부 데이터를 최신 정보인 것처럼 재사용하지 않음. 외부 데이터의 출처·조회 시점·적용 범위를 확인.

### 오류 감지 및 자가 성찰의 필수 흐름

`오류 감지 → 원인 분석 → 수정 전략 선택 → 재실행 → 검증`

1. **오류 감지:** 규칙/휴리스틱/LLM 판정 등 적용할 기준과 결과 정의.
2. **원인 분석:** 어떤 입력·도구 결과·상태 때문에 잘못 판단했는지 확인.
3. **수정 전략 선택:** 필요 시 재질문, 도구 인자·프롬프트 조정, 도구 변경, 대체 경로 선택.
4. **재실행:** 수정한 입력/상태/정책을 실제 다음 실행에 반영.
5. **검증:** 처음 정의한 판정 기준으로 재검사한 뒤 성공·재수정·실패·추가 질문 중 다음 행동 결정.

추가 조건:

- **할루시네이션, 도구 선택 오류, 파라미터 누락, 응답 불일치** 등 다룰 오류를 구체적 기준으로 판정한다.
- 오류 유형별 **재시도 횟수 및 대체 전략**을 정한다.
- 프롬프트·파라미터 등을 수정한 경우 **버전과 변경 이유**를 기록한다.
- 단순 통신 실패 재시도와 **판단 오류를 고치는 자가 성찰 재실행**을 구분한다.
- 한 대표 오류 사례에 대해 피드백 루프의 단계별 입력·출력·수정·검증 결과를 실제 실행 기록과 연결한다.

### D-01. 에이전트 아키텍처 설계서 — [필수 제출 문서 1]

최종 코드와 일치해야 하며, 다음 내용을 담는다.

- StateGraph의 각 노드에 대한 역할, 입력·출력, 다음 노드로 이동하는 조건.
- **인지 → 판단 → 행동 → 검증**의 전체 흐름; 정상 경로, 오류 경로, 대체 경로를 엣지로 표현.
- 도구를 호출할지 결정하는 정책, 사용자 의도 및 정보 충분성의 판단 기준.
- Function Calling/Tool Use의 **도구 선택 → 호출 → 결과 처리 → 다음 노드 결정**을 **시퀀스 다이어그램 또는 상태 흐름도**로 설명.
- 단기·장기 기억 조회·저장, 컨텍스트 구성, 요약 전략과 그래프 연결.
- 상태 객체의 필드·타입 힌트·갱신 지점.
- 오류 감지·수정·재실행·종료 한도, 정상·실패·추가 질문 경로.
- 그림에 표현한 노드/상태/도구가 실제 코드와 대응하는 설명.

### D-02. 에이전트 시험 결과 보고서 — [필수 제출 문서 2]

반드시 포함:

1. 대표 사용 흐름, 정상/오류 유형, 시험 입력과 기대 결과.
2. **측정 전에 정의한** 판정 기준 및 시험 환경/조건.
3. 초기 버전의 **실제** 도구 선택·상태 전이·오류·최종 결과 기록.
4. 수정한 프롬프트·인자·정책 등의 버전, 변경 이유, 적용 결과.
5. **같은 시험 입력과 판정 기준**으로 자가 성찰 적용 전후를 비교한 결과.
6. 수치, 대표 성공·실패 사례, 개선되지 않은 부분 및 한계.
7. 다음의 **4개 필수 지표**의 측정 정의와 적용 전후 결과.

| 필수 지표 | 지표에 기록해야 할 산정 정보 |
|---|---|
| **태스크 완료율** | 시나리오별 완료 조건, 완료 건수, 총 시험 건수 |
| **도구 선택 정확도** | 정답/허용 도구 조합, 불필요한 호출 및 호출 누락 판정 기준, 적중 건수와 총 판정 건수 |
| **응답 일관성(Consistency) 점수** | 사실·사용자 조건·응답 구조 중 비교 항목, 반복 실행 조건, 점수 산정 방식 |
| **평균 재시행 횟수** | 최초 실행 이후의 추가 실행을 세는 단위, 각 횟수와 평균 산정 시험 수 |

**측정 유의사항:**

- 수정하려는 항목을 제외한 모델·도구·주요 조건은 가급적 동일하게 유지하고, 차이는 명시한다.
- 도구의 원시 반환값, LLM의 답변, 사람의 판정 결과를 구분한다.
- 준비된 응답이나 고의로 실패를 주입한 시험은 실제 API 조회 결과와 구분하여 표시한다.
- 수치는 **실제 실행 근거**로 계산하며, 측정하지 않은 값은 `미측정`으로 기록한다. 개선 없는 결과도 누락하지 않는다.

### D-04. 배포 서비스 주소 — [필수 제출]

- 다른 팀이 접속 가능한 **사용자 화면 URL**과 사용 방법 제공.
- 배포된 프론트엔드가 **실제 백엔드**에 연결되고 실제 외부 API 및 기억 저장소를 이용할 수 있어야 함.
- 사용자 화면에서 정상 요청, 정보 부족, 도구 실패, 판단 오류 수정 경로를 체험 가능해야 함.
- 데이터 출처/시점, 추가 확인 필요 상태, 오류 안내를 이해할 수 있게 표시.
- 로컬뿐 아니라 공유한 배포 주소에서 대표 흐름을 다시 확인.
- API 키·토큰·개인정보는 화면 코드·로그·발표 자료에 노출하지 않음.
- 로그인 등 접근 조건이 있으면 체험 가능한 접근 방법을 제공.
- **Render는 배포 지원 서비스**일 뿐, Render만 사용해야 한다는 조건은 없음.

### D-05. PPT 및 시연 — [필수 제출/발표]

발표에 포함:

1. 해결할 사용자 문제와 대표 사용 흐름.
2. StateGraph, 도구, 기억, 상태의 설계 및 선택 이유.
3. 실제 서비스 동작, 판단 오류 감지→수정→재실행→검증 과정.
4. 자가 성찰 적용 전후 성능 결과, 개선점, 남은 한계, 팀원별 기여.

시연에는 `사용자 요청 → 도구 호출·상태 전이 → 최종 결과·검증 결과`를 포함. 오류 사례에서는 감지 근거, 수정 전략, 재실행 결과를 제시. **발표 수치는 시험 보고서의 실제 수치와 일치**시킨다.

## 4. 협업·개발·통합 조건 — [필수 운영/검증]

- 팀원별 담당 작업 및 공유 시점, 코드 리뷰 방법, 장애/도움 요청 방식 합의.
- GitHub 팀 저장소에서 `작업 등록 → 브랜치 작업 → PR·설명 → 리뷰 → 병합` 사용.
- 상태 객체·도구 스키마·그래프 등 공통 부분 수정 전 담당자와 협의.
- 담당자는 변경 이유, 입력·출력, 상태 변화, 오류 처리 방식을 설명하고 실제 실행할 수 있어야 함.
- 검토자는 정상/오류 시나리오의 결과를 확인하고 요청한 수정을 반영한 뒤 병합.
- **AI를 이용한 코드 생성·수정·디버깅은 허용**되지만 사람이 핵심 동작을 설명·수정·실행할 수 있어야 함.
- 통합할 때 정보 부족·도구 실패·조건 위반에서 다음 노드 전이와 동작을 확인.
- 상태·도구·전이 변경 시 **코드 + 설계서 + 시험 기록**을 함께 갱신.
- 권장 구현 순서(원문 안내): 대표 요청 하나를 `화면 → 에이전트 → 도구 → 검증 → 결과`로 먼저 연결한 후 기억 및 오류 수정 경로를 추가.

## 5. 주제 선택의 자유도와 비필수 사항

### [주제 자유]

- 공식 프로젝트명은 **복합 API 연계 일정 조정 에이전트**이지만 실제 서비스 주제를 확장해 정할 수 있음.
- 원문 예시: **식단 관리**, **자격증 준비**, **정보 탐색·추천**, 여행/회의 등.
- 핵심은 `조건 파악 → 필요한 외부 정보 조회 → 계획/답변 생성 → 검증·수정` 흐름과 공통 기술 요건 유지.

### [미지정 또는 예시 — 과제 필수 조건으로 오해 금지]

- **LangChain 사용:** 별도 필수 조건으로 명시되지 않음.
- **RAG 또는 벡터 데이터베이스:** 필수 조건으로 명시되지 않음.
- **멀티 에이전트 구조:** 명시되지 않음. 필수는 **다중 도구(Multi-tool) 선택**임.
- **특정 LLM 공급자/모델:** 명시되지 않음.
- **외부 API의 정확한 개수, 제품명:** 정해져 있지 않음. 다중 도구 선택과 실제 API 활용 조건은 준수.
- **기억 저장소 제품/DB 선택:** 특정 제품 명시 없음. 기능 요건은 존재.
- **재시도 최대 횟수:** 특정 숫자 명시 없음. 팀이 정의하고 검증해야 함.
- **정해진 노드명(Start, Tools, Decision, End 등)이나 상태 필드명:** 예시일 뿐 고정 이름 아님.
- **Render:** 지원되는 배포 수단이지 필수 호스팅 지정 아님.
- **특정 프론트엔드 프레임워크:** 명시되지 않음.
- **4개 성능 지표의 최소 합격 점수나 목표 상승 폭:** 문서에 특정 값 없음. 측정·비교·기록은 필수.
- **설계서/시험 보고서의 특정 파일 확장자:** 지정 없음.

> 위 항목 중 실제 구현에 필요한 기술·서비스·범위는 사용자 또는 팀이 결정할 사항이다. LLM은 이를 '원문이 지시한 필수 요구'로 바꾸지 말아야 한다.
