# 실제 API 확인 — 1. 일반 문의 흐름 결과 (2026-11-10, Issue #62)

계획 `docs/plans/gmail-quote-mvp.md` 16절의 1번(로그인 → 감시 등록 → 상대방 메일 → 후보 2~3개 → 승인 → 같은 스레드 발송)을 Render 배포 주소에서 실제 Gmail·Gemini로 확인한 결과다. 16절의 2~4번은 따로 기록한다.
레포가 공개 레포이므로 실제 이메일 주소·이름·키는 적지 않는다(A·B 계정으로만 적음).

## 기록 파일 (이 폴더)
`/runs/{run_id}/export`로 내려받은 개인정보 가린 실행 기록이다. 파일 이름은 내보내기 코드(`app/runlog/export.py`)가 만든 그대로다: `<YYYYMMDD-HHMM>_<시나리오, 실제 메일이면 live>_<refl-on|refl-off>_<run_id 앞 8자>.jsonl`, 시각은 UTC(KST −9시간).

| 회차 | 파일 | 종료 |
|---|---|---|
| 1차 | `20261110-0600_live_refl-on_c82cf5a8.jsonl` | `failed` |
| 2차 | `20261110-0610_live_refl-on_d9e1ee93.jsonl` | `failed` |
| 3차 | `20261110-0642_live_refl-on_c845e0d3.jsonl` | `awaiting_approval` → 승인·발송 성공 |

## 시험 환경
- 서버: Render `https://aio3-gmail-quote.onrender.com` (무료, Singapore)
- 계정: A = 앱에 로그인한 테스트 Gmail(사용자 역할), B = 발신용 테스트 Gmail(상대방 역할)
- 설정 화면(`/settings`): 공급자·단가표 입력 완료(일반 문의 흐름에서는 쓰지 않음)
- 성찰: 켬(모든 실행)
- 모델: 1·2차 `gemini-3.8-flash` → 3차부터 `gemini-3.6-flash` (PR #94, main 2a992de). 프롬프트 버전 `analyze_email.v1`·`draft_replies.v2`

## 발견한 문제와 조치
1. 감시 등록 HTTP 403 (해결, 코드 변경 없음)
   - 증상: `/inbox`에 '새 메일 알림 등록에 실패했습니다. 화면을 다시 열면 다시 시도합니다.', 배지 '알림 확인 필요'. A 계정에는 메일이 도착했지만 앱에는 아무것도 생기지 않음. Render Logs `사용자 1: Gmail 감시 등록 실패 (HTTP 403)`가 서버 인스턴스가 바뀐 뒤에도 반복.
   - 원인: Pub/Sub 토픽 `gmail-notify`의 권한에 '소유자(기존)'만 있고 `gmail-api-push@system.gserviceaccount.com`의 Pub/Sub 게시자 역할이 없었다. Gmail API는 켜져 있었다. `.work/design/api-choice.md` '콘솔 설정 결과'에는 게시자를 줬다고 적혀 있었으나 실제로는 빠져 있었다(이 PR에서 그 줄에 사실을 덧붙임).
   - 조치: 콘솔 → Pub/Sub → 주제 `gmail-notify` → 정보 패널 → 권한 → 주 구성원 추가(역할 Pub/Sub 게시자). 이후 `/inbox` 새로고침 두 번 → '새 메일 알림 켜짐'.
   - 참고: 등록 전에 온 메일은 처리하지 않는다(설계대로). 첫 테스트 메일은 다시 보내야 했다.
2. Gemini 호출 503 (해결, PR #94 병합)
   - 증상: 받은 메일 '오류'. 실행 기록에서 `analyze_email`의 LLM 호출 3회가 모두 `error_kind=network`로 실패해 `finish_failed`(`call_retries` 2). 시도별 시간(재시도 대기 1초·2초 제외) 1차 약 18.4s/0.7s/0.8s, 2차 약 1.9s/1.5s/18.3s(1~2초 실패는 시간 초과가 아님).
   - 원인 확인: 요청자 PC에서 같은 키로 `hello` 한 단어 요청 → `gemini-3.8-flash` 5회 모두 HTTP 503(0.9~7.9초). 같은 때 `gemini-3.6-flash` 3회 200(약 2.1~2.4초), `gemini-3.5-flash-lite` 3회 200, `gemini-3.1-flash-lite` 3회 503.
   - 조치: 요청자가 `gemini-3.6-flash`로 교체를 정함 → PR #94(기본 모델 3.6, 환경변수 `GEMINI_MODEL`로 덮어씀). 병합·배포 뒤 3차에서 정상.
   - 함께 한 일: 확인 중 이전 Gemini 키가 대화에 노출되어, 결제 없는 프로젝트에서 새 키를 만들고 Render `GEMINI_API_KEY`를 바꿨다(요청자).

## 고칠 후보와 결정
결정(2026-11-10, 요청자): 오류 코드 두 줄 → Issue #95, 스레드 화면 상태 → Issue #96, `/runs` 표시 → Issue 안 만듦(설계대로, 발표 때 설명), 처리 시간 → 보류(위 노드별 소요를 보고 다시 정함), 문서 정정 → 이 기록 PR에 포함.

- LLM 오류의 실제 HTTP 코드·메시지가 실행 기록·서버 로그 어디에도 남지 않아 503을 기록만으로 알 수 없었다(`app/llm/client.py`는 오류 종류만 남김). 짧은 코드(예: `HTTP 503`)를 `retry`·`error` 줄 detail에 남기면 다음 진단이 빨라진다. → #95
- 감시 등록 실패 로그도 HTTP 코드만 남겨 403의 두 원인(API 꺼짐/게시자 권한 없음)을 구분하지 못했다. → #95

- 성찰 켬 상태 처리 시간 약 25초(발송 → 후보 준비 약 43초). 노드별 소요는 위 표. → 보류
- 문서 정정: `.work/design/api-choice.md` '콘솔 설정 결과'의 게시자 권한 줄에 2026-11-10 확인 때 빠져 있어 추가했다는 사실을 덧붙였다(이 PR).
